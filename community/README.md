# MoteDB Community

> One library file is your multimodal database.
> This is where the people running MoteDB on robots, AR glasses, industrial
> arms and edge AI devices meet to talk about vectors, time series, text and
> binary data.

## Where to go

| Channel | Use it for | Best if you | Status |
|---|---|---|---|
| **GitHub Discussions** | Questions, ideas, Show and Tell | You want your question to stay searchable — and answerable by an AI assistant months later | Open |
| **GitHub Issues** | Bug reports, reproducible feature requests | You hit a definite, reproducible problem | Open |
| **Mailing list** | Release notices + the community newsletter | You want to follow along passively without joining anything | Subscribe form opening soon |

**first response within 48 hours**.

If you need the latest version without joining anything: new versions are
tagged in the repository, and every change is written up in
[`CHANGELOG.md`](https://github.com/motedb/motedb/blob/main/CHANGELOG.md).

## What each channel is for

We keep these deliberately distinct so you don't wait in the wrong place:

- **Deep, async questions → Discussions.** Answers here get indexed by search
  engines and retrieved by AI assistants. One answer helps many people.
- **Definite bugs → Issues.** Templates, reproduction steps, status tracking.
- **Live chat and quick questions → the chat channel.** But note: **chat does
  not persist.** If a technical conclusion matters, we will write it up
  afterwards in a FAQ or a doc.
- **Versions and the monthly report → the mailing list.** One email a week at
  most. No notification spam.

## The mailing list

**The mailing list is the project's main broadcast channel.** Each email
contains:

1. This week's release and what changed
2. One real usage story / Show & Tell
3. One technical opinion or a bug we hit and what it taught us
4. The community monthly report (one per month): contributor credits, roadmap
  updates, plans for next month

> Why a mailing list and not only a chat server? Because **a lot of people
> don't join forums.** Researchers, technical decision-makers inside companies,
> students evaluating a database — they will subscribe to a newsletter but
> won't join a chat room. The mailing list is the only low-cost way to reach
> that group.

## Show and Tell

Built something with MoteDB? Write it up.

**The easy way:** open a post in
[Discussions → Show and Tell](https://github.com/motedb/motedb/discussions).

**What we will do**:
- Pick one a week for the website showcase and the mailing list
- Help you distribute it on your target platform (掘金 / 知乎 / 公众号 /
  dev.to / X / LinkedIn)
- Make you a community Champion, if you want the role

**What we would like you to include**:
- What you are building (the scenario, not the tech stack)
- Why you picked MoteDB
- A small piece of real SQL or code
- The parts that bit you — **this is the most valuable part**, because it
  saves someone else an afternoon

> One user, one small tool, one successful query — that's worth writing up.
> **Every community starts with its first Show & Tell.**

## Want to help? Three ways in

### 1. Ask a good question

Not a bug? Still welcome. "Is this the right way to write it", "is there a
cleaner version", "why was it designed this way" — **questions like these are
how we find the gaps in our documentation.**

Accepted questions get written into the FAQ / best-practices doc, with your
name on them.

### 2. Claim a task

Issues labelled `good first issue` or `help wanted` are explicit entry points.
To claim one: comment "I'd like to work on this" on the issue.

**The three easiest starting points**:
- 📖 **Doc fixes** — typos, outdated APIs, missing examples
- 🧪 **More test cases** — especially differential-testing scenarios
- 🐍 **Python examples** — port a Rust example to Python

### 3. Write a Show & Tell

See the section above.

## Community expectations

What we expect:

- Respect for people at different experience levels
- Criticising the work, not the person
- Accepting constructive criticism
- Helping newcomers
- Not treating chat like a support ticket queue — **if you can search it,
  search it first**

The full rules are in [`CODE_OF_CONDUCT.md`](../CODE_OF_CONDUCT.md).

## How you get credit

| What you did | Where it shows up |
|---|---|
| Asked a good question | The FAQ / examples, with your name |
| Reported a bug | The fix's CHANGELOG entry, with your name |
| Merged a PR | CHANGELOG author credit + the contributor list in the README |
| Contributed consistently | Commit rights + public recognition |
| Wrote a Show & Tell | The website showcase + the mailing list spotlight |

> Most open-source contributors contribute once or twice and then disappear.
> **The only thing that keeps them is being seen.**
